# @Transactional의 옵션

- **단순 커밋/롤백을 넘어선 세밀한 제어**:
  - 읽기 전용 최적화, 전파 방식, 롤백 대상 예외까지 지정 가능
- **`readOnly = true`**:
  - 조회 전용 메서드에 지정하면 변경 감지 스냅샷 비교와 플러시를 생략해 성능 최적화
- **`rollbackFor`**:
  - 스프링 기본 정책은 `RuntimeException`(및 `Error`)에서만 자동 롤백하므로, 체크 예외에서도 롤백이 필요하면 명시해야 함

---
layout: default
---

# readOnly로 조회 성능 최적화

```java
@Transactional(readOnly = true)
public List<User> findUsers() {
    return userRepository.findAll();
}
```

layout: default
---

# 체크 예외까지 롤백 대상으로 지정

```java
@Transactional(rollbackFor = Exception.class)
public void register(User user) {
    userRepository.save(user);
}
```

# 전파 속성(Propagation)

> **전파 속성 (Propagation)**
>
> 이미 진행 중인 트랜잭션이 있는 상태에서 `@Transactional` 메서드가 추가로 호출될 때, 기존 트랜잭션에 합류할지 새로 시작할지를 결정하는 옵션

---
layout: default
---

# REQUIRED vs REQUIRES_NEW

| 옵션 | 동작 |
| :--- | :--- |
| `REQUIRED` (기본값) | 진행 중인 트랜잭션이 있으면 참여, 없으면 새로 시작 |
| `REQUIRES_NEW` | 기존 트랜잭션을 보류하고 완전히 독립된 새 트랜잭션 시작 |

- `REQUIRES_NEW`는 메인 로직이 롤백되어도 로그 기록 같은 하위 트랜잭션은 별도로 커밋되게 할 때 사용

---
layout: default
---

# self-invocation의 한계

> **self-invocation 문제**
>
> `@Transactional`은 스프링이 생성한 프록시 객체를 거쳐야 동작하므로, 같은 클래스 내부에서 `this.otherMethod()`를 직접 호출하면 프록시를 거치지 않아 애노테이션이 무시됨

---
layout: default
---

# 프록시를 거치지 않는 내부 호출

```java
@Service
public class UserService {
    public void outer() {
        this.inner();  // 프록시 미경유 → @Transactional 무시
    }

    @Transactional
    public void inner() {}
}
```

- **해결 방법**: 트랜잭션이 필요한 메서드를 별도의 빈(다른 클래스)으로 분리해 프록시를 통해 호출

---
layout: default
---

# Spring JDBC / MyBatis와의 트랜잭션 비교

- **공통 추상화**:
  - `@Transactional`은 JPA 전용이 아니라 `PlatformTransactionManager`라는 Spring Data Access 공통 추상화의 일부
- **체감되는 차이**:
  - Spring JDBC/MyBatis는 SQL 호출 즉시 DB에 반영되지만, JPA는 커밋(flush) 시점에야 변경 감지로 SQL이 나감

layout: default
---

# 기술별 트랜잭션 매니저 구현체

| 데이터 접근 기술 | 트랜잭션 매니저 |
| :--- | :--- |
| Spring JDBC / MyBatis | `DataSourceTransactionManager` |
| JPA | `JpaTransactionManager` |

# Pageable / Sort

> **Pageable / Sort**
>
> Spring Data JPA가 제공하는 페이징·정렬 요청 객체로, Repository 메서드 파라미터로 전달하면 `LIMIT`/`OFFSET`과 `ORDER BY`가 포함된 SQL을 자동 생성

---
layout: default
---

# 페이징을 지원하는 Repository 메서드

```java
public interface UserRepository extends JpaRepository<User, Long> {
    Page<User> findByAgeGreaterThan(int age, Pageable pageable);
}
```

---
layout: default
---

# PageRequest로 요청 객체 생성

```java
Pageable pageable =
        PageRequest.of(0, 10, Sort.by("userName").ascending());
Page<User> result =
        userRepository.findByAgeGreaterThan(20, pageable);
```

- `PageRequest.of(page, size, sort)`: 0부터 시작하는 페이지 번호, 페이지당 개수, 정렬 기준을 조합

---
layout: default
---

# 전체 건수가 필요한가에 따른 반환 타입 선택

| 구분 | `Page<T>` | `Slice<T>` |
| :--- | :--- | :--- |
| COUNT 쿼리 | 실행함 (`totalElements`, `totalPages` 제공) | 실행 안 함 |
| 판단 방식 | 전체 건수 기준 | 요청 크기보다 1건 더 조회해 `hasNext()`만 판단 |
| 적합한 화면 | 전체 페이지 수 표시(게시판) | 무한 스크롤 |

# JPA Auditing이란

> **JPA Auditing**
>
> 엔티티가 생성·수정될 때마다 등록일시·수정일시 같은 메타데이터를 개발자가 직접 채우지 않아도 Spring Data JPA가 자동으로 채워 주는 기능

# Auditing 기능 활성화

```java
@Configuration
@EnableJpaAuditing
public class JpaConfig {
}
```

- 선언이 누락되면 `@CreatedDate` 등이 채워지지 않고 `null`로 남음

# 공통 상위 클래스로 필드 중복 제거

```java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {
    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}
```

---
layout: default
---

# @MappedSuperclass의 역할

- **테이블로 매핑되지 않음**:
  - 자신은 테이블이 되지 않고, 상속한 엔티티에게 필드(컬럼)만 물려주는 공통 상위 클래스
- **적용 방식**:
  - `class User extends BaseEntity`처럼 상속만 하면 `createdAt`/`updatedAt`이 자동으로 추가됨

---
layout: default
---

# 마지막 상태만 기록한다는 한계

- **덮어쓰기 방식**:
  - JPA Auditing은 "누가 언제 마지막으로 바꿨는가"만 컬럼 하나에 덮어써서 기록
- **중간 변경 이력이 필요하다면**:
  - 별도의 이력 테이블을 두거나 Hibernate Envers 같은 변경 이력 추적 라이브러리를 함께 고려

# QueryDSL이란

> **QueryDSL**
>
> 문자열이 아닌 자바 코드(메서드 체이닝)로 쿼리를 조립하는 타입 세이프(Type-safe) 쿼리 빌더

- 오타·타입 불일치를 컴파일 시점에 잡아낼 수 있고, 조건별 동적 쿼리 조합에 강점

---
layout: default
---

# OpenFeign 포크로의 전환

- **원조 프로젝트의 정체**:
  - `com.querydsl`은 유지보수가 크게 둔화되어 최신 Spring Boot와의 호환 문제 발생
- **현재 권장 의존성**:
  - 커뮤니티가 이어받은 `io.github.openfeign.querydsl` 포크 사용이 공식적으로 권장됨

---
layout: default
---

# QueryDSL 의존성 추가

```xml
<dependency>
    <groupId>io.github.openfeign.querydsl</groupId>
    <artifactId>querydsl-jpa</artifactId>
    <classifier>jakarta</classifier>
</dependency>
```

# Q-타입: 필드 접근용 메타 클래스

- **애노테이션 프로세서(APT)**:
  - `@Entity` 클래스를 컴파일 시점에 스캔해 `QUser`처럼 정적 메타 클래스(Q-타입)를 자동 생성
- 이 Q-타입을 통해 실제 쿼리를 조립

---
layout: default
---

# JPAQueryFactory로 조립하는 동적 쿼리

```java
JPAQueryFactory queryFactory = new JPAQueryFactory(entityManager);
QUser user = QUser.user;

List<User> result = queryFactory
        .selectFrom(user)
        .where(user.age.gt(20).and(user.userName.like("%김%")))
        .orderBy(user.userName.asc())
        .fetch();
```

---
layout: default
---

# 동적 쿼리에서의 강점

- **조건별 자바 코드 분기**:
  - 검색 조건이 있을 때만 `where` 절에 조건을 추가(`BooleanBuilder` 등)
  - JPQL 문자열을 조건별로 이어 붙이지 않고도 자바 코드 그대로 분기 처리 가능

# MyBatis vs JPA(+QueryDSL): 선택 기준

---
layout: default
---

# 자동화 대 제어력의 트레이드오프

- **JPA**:
  - 단순 CRUD와 연관관계 매핑을 자동화해 생산성을 높이는 대신 실행 SQL을 직접 눈으로 보기 어려움
- **MyBatis**:
  - SQL을 직접 작성·제어하는 대신 매핑 보일러플레이트가 상대적으로 많음
- QueryDSL 도입 이후에도 이 구도는 근본적으로 유지됨

---
layout: default
---

# 실무에서의 조합

- **JPA + QueryDSL**:
  - 단순 CRUD는 Query Methods로, 복잡한 동적 검색·통계성 조회는 QueryDSL로 처리하는 조합이 표준적인 해법
- **MyBatis가 여전히 선호되는 경우**:
  - 복잡한 리포팅 쿼리, DB 벤더 특화 문법, 대량 배치 처리처럼 SQL 미세 제어와 실행계획 예측이 중요한 영역

---
layout: default
---

# 상황별 선택 기준 비교

| 구분 | JPA(+QueryDSL) | MyBatis |
| :--- | :--- | :--- |
| 생산성 | 단순 CRUD 자동화 | SQL 직접 작성(보일러플레이트 많음) |
| SQL 제어력 | 상대적으로 낮음 | 세밀한 제어·실행계획 예측 용이 |
| 강점 영역 | 도메인 CRUD, 타입 세이프 동적 쿼리 | 복잡 리포팅, 벤더 특화 문법, 대량 배치 |

---
layout: default
---

# 팀·프로젝트 단위의 하이브리드 구성

- 두 기술은 상호 배타적이지 않음
- 하나의 프로젝트 안에서 도메인 CRUD는 JPA로, 통계·리포트 등 읽기 전용 대량 조회는 MyBatis로 병행 사용하는 구성도 드물지 않음

---
layout: default
---

# 참고: jOOQ라는 제3의 선택지

- **SQL을 자바 코드로 그대로 표현**:
  - QueryDSL처럼 동적 쿼리를 코드로 조립하면서도 JPQL이 아닌 실제 SQL(윈도우 함수 등)에 가깝게 다룰 수 있음
- MyBatis의 SQL 제어력과 QueryDSL의 타입 세이프함을 절충한 대안으로 소개되기도 함

# 학습 요약 (Summary)

- **@Transactional 심화**:
  - `readOnly`/`rollbackFor`로 세밀한 제어, self-invocation은 빈을 분리해 프록시를 경유하도록 해결
- **페이징과 정렬**:
  - `Pageable`/`Sort`로 자동 생성, 게시판은 `Page<T>`, 무한 스크롤은 `Slice<T>`
- **Auditing**:
  - `@MappedSuperclass` + `@EnableJpaAuditing`으로 등록일/수정일을 자동 관리
- **QueryDSL과 MyBatis**:
  - 단순 CRUD는 JPA, 복잡한 동적 쿼리는 QueryDSL, 세밀한 SQL 제어가 필요하면 MyBatis를 병행
