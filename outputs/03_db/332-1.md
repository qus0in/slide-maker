# 왜 개선이 필요한가

- LLM이 틀리는 이유는 크게 두 가지로 나뉨

# 프롬프트 엔지니어링

> **프롬프트 엔지니어링 (Prompt Engineering)**
>
> 모델의 가중치를 바꾸지 않고 입력 지시문만 다듬어 원하는 출력을 유도하는 기법

- 별도 학습·인프라 비용 없이 즉시 적용 가능해 가장 먼저 시도

# Lost in the middle

> **Lost in the middle**
>
> 컨텍스트가 길어질수록 모델이 문서의 처음과 끝은 잘 참고하지만 중간 내용은 놓치기 쉬워지는 현상

# 도구 호출과 파인튜닝

- **도구 호출 (Tool/Function Calling)**:
  - 모델이 등록된 함수를 실행해 실시간 데이터나 계산 결과를 가져오게 함
- **파인튜닝 (Fine-tuning)**:
  - 가중치 자체를 갱신해 모델 역량을 바꾸는 방식
  - 학습 비용이 크고 지식이 학습 시점에 고정되어 자주 바뀌는 문서에는 부적합

# RAG 정의

> **RAG (Retrieval-Augmented Generation, 검색 증강 생성)**
>
> 질문에 바로 답하게 하지 않고 문서 저장소에서 관련 조각을 검색해 프롬프트에 실은 뒤 그 근거 안에서 답을 생성하게 하는 기법

- 검색(Retrieval)과 생성(Generation)을 하나의 흐름으로 묶은 것

---
layout: default
---

# RAG와 파인튜닝의 지식 주입 방식 비교

- 파인튜닝은 시험 전에 내용을 통째로 암기시키는 것과 비슷함
- RAG는 시험장에 참고 자료를 들고 들어가 필요한 페이지만 펼쳐 보는 것과 비슷함
- 암기가 아니라 "찾아서 근거로 삼는" 방식이라 최신 자료 반영이 훨씬 쉬움

---
layout: default
---

# 필요한 이유 ① 지식 컷오프

- LLM은 학습 시점 이후의 정보나 사내 문서를 애초에 알지 못함
- 새 정책, 최근 릴리스 노트, 비공개 문서는 물어봐도 답할 수 없음
- 검색으로 최신 문서를 붙여 주면 이 한계를 그때그때 보완 가능

---

# 필요한 이유 ② 환각

> **환각 (Hallucination)**
>
> 모델이 모르는 내용을 그럴듯하게 지어내어 사실처럼 답하는 현상

- "주어진 컨텍스트에만 근거해 답하고 없으면 모른다고 하라"는 지침과 근거 문서를 함께 제공해 억제

# 다른 기법 사이에서 RAG의 위치

- 파인튜닝은 모델 역량 자체를 바꾸는 접근
- 긴 컨텍스트는 자료를 통째로 밀어 넣는 접근
- RAG는 모델은 그대로 두고 필요한 지식 조각만 골라 넣는 접근

# 임베딩 정의

> **임베딩 (Embedding)**
>
> 텍스트를 의미가 보존된 고차원 실수 벡터로 변환하는 것

- 예: 768개 또는 1536개의 float 배열로 문장 하나를 표현

---
layout: default
---

# 벡터 공간에서 의미를 표현하는 방식

- 임베딩은 문장을 숫자 목록으로 바꾸고, 그 목록을 공간의 한 점처럼 다룸
- 의미가 비슷한 문장은 가까운 곳에, 다른 문장은 먼 곳에 놓임
- 그래서 글자가 달라도 의미가 가까운 문서를 찾을 수 있음

---
layout: default
---

# 키워드 검색과 의미 검색의 차이

> **의미 검색 (Semantic Search)**
>
> 글자 일치가 아니라 벡터 공간에서의 거리로 관련 문서를 찾는 검색 방식

- `LIKE '%강아지%'`는 글자가 일치해야 하지만, 의미 검색은 "우리 집 멍멍이"로도 "반려견 사료 안내"를 찾아냄

---
layout: default
---

# 임베딩 차원과 동일 모델 원칙

- 임베딩 벡터의 길이는 모델마다 고정됨
- 적재와 질의는 같은 모델·같은 차원을 사용해야 함
- 모델을 바꾸면 기존 벡터와 비교할 수 없어 전체 재임베딩이 필요함

# 유사성 검색 정의

> **유사성 검색 (Similarity Search)**
>
> 질문 벡터와 가장 가까운 문서 벡터 K개를 찾는 연산

- 벡터 공간에서 "가까움"을 실제 검색 결과로 바꾸는 핵심 단계

---
layout: default
---

# Top-K와 유사도 임계값

| 파라미터 | 의미 |
| :--- | :--- |
| Top-K | 검색할 결과 개수, 실습에서는 4~5 기본 |
| 유사도 임계값 | 점수가 기준(예: 0.7) 미만이면 버림 |

- K가 작으면 근거 부족, 크면 노이즈와 토큰 비용 증가

---
layout: default
---

# 코사인 유사도로 가까움 측정

> **코사인 유사도 (Cosine Similarity)**
>
> 두 벡터가 가리키는 방향이 얼마나 비슷한지 재는 척도

- 값이 클수록 의미가 가깝다고 해석함

---
layout: default
---

# 완전 탐색과 ANN 검색

- **완전 탐색 (Exact/Brute-force)**: 모든 벡터와 거리를 계산, 정확하지만 데이터가 늘면 느려짐
- 수천 건 규모의 실습에서는 인덱스 없이도 충분히 빠름
- 데이터가 많아지면 ANN 인덱스로 검색 후보를 줄임

---
layout: default
---

# ANN 인덱스란 무엇인가

> **ANN (Approximate Nearest Neighbor, 근사 최근접 이웃)**
>
> 모든 벡터를 비교하지 않고, 가까울 가능성이 높은 후보만 찾아 검색 속도를 높이는 방법

- 결과가 항상 완벽히 동일하지 않을 수 있지만 대규모 데이터에서 훨씬 빠름
- `HNSW`는 이웃 그래프를 따라가고, `IVFFlat`은 가까운 군집 일부만 탐색함
- 실습에서는 정확도와 운영 편의성이 좋은 `HNSW`를 기본 선택

---
layout: default
---

# HNSW와 IVFFlat

| 인덱스 | 특징 |
| :--- | :--- |
| HNSW | 다층 그래프로 이웃을 따라 탐색, 속도·정확도 모두 우수해 사실상 기본 선택지 |
| IVFFlat | 군집으로 나눈 뒤 가까운 일부만 탐색, 생성은 가볍지만 데이터가 쌓인 뒤 만들어야 품질이 나옴 |

# 벡터 DB 정의

> **벡터 데이터베이스 (Vector Database)**
>
> 고차원 벡터를 저장하고 유사도 기반으로 빠르게 검색하는 데 특화된 데이터베이스

- 벡터·원문·메타데이터를 함께 보관하고 ANN 인덱스와 필터링을 제공

# 일반 RDB와 무엇이 다른가

- 일반 RDB의 B-Tree 인덱스는 정렬 가능한 값(숫자, 문자열)에 최적화됨
- "의미가 가깝다"는 개념은 정렬 기준이 아니라서 B-Tree로는 처리할 수 없음
- 벡터 DB는 거리 기반 ANN 인덱스로 이 문제를 해결

# 메타데이터 필터링의 중요성

- "이 부서 문서 중에서"처럼 조건을 먼저 좁힌 뒤 유사도 검색을 수행
- 검색 범위를 줄여 정확도와 속도를 함께 높임
- 사용자 권한별로 접근 가능한 문서만 걸러내는 데도 활용

# 검색 엔진과 RAG는 무엇이 다른가

- 검색 엔진은 문서 목록을 사람에게 돌려주면 목적 달성
- RAG는 그 검색 결과를 LLM에 먹여 최종 답변 문장을 만드는 것이 목적
- RAG는 검색 엔진을 대체하는 기술이 아니라 검색을 부품으로 포함하는 더 큰 구조

# pgvector 선택 기준: PostgreSQL 통합과 운영 단순화

- **하나의 DB로 통합**:
  - 별도 벡터 DB 서버 없이 기존 업무 테이블과 벡터를 같은 PostgreSQL에 보관
- **SQL과 트랜잭션**:
  - JOIN·WHERE 활용, 문서 저장과 벡터 저장을 하나의 트랜잭션으로 처리
- **학습 곡선과 비용**:
  - 새 쿼리 언어·SDK가 필요 없고 Neon·Aiven·Supabase 무료 플랜이 지원

# 확장 활성화

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS hstore;
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
```

# 확장은 DB 단위로 활성화된다

- 확장은 서버 전체가 아니라 데이터베이스 단위로 활성화됨
- 다른 DB에 접속했다면 위 CREATE EXTENSION을 다시 실행해야 함
- IntelliJ Database Tool 또는 DBeaver의 SQL Editor에서 실행
- Neon·Aiven은 허용 확장 목록에 pgvector를 미리 포함해 별도 권한 상승 불필요

# 벡터 컬럼을 가진 테이블

```sql
CREATE TABLE vector_store (
    id        uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
    content   text,
    metadata  json,
    embedding vector(1536)
);
```

# 학습 요약 (Summary)

- **RAG의 핵심 흐름**:
  - 문서를 조각내 임베딩하고, 질문과 의미가 가까운 조각을 검색해 답변 근거로 사용
- **벡터 검색**:
  - 코사인 유사도와 Top-K로 관련 문서를 고르며, 데이터가 커지면 ANN 인덱스로 검색 후보를 줄임
- **pgvector**:
  - PostgreSQL에 벡터 타입과 HNSW 인덱스를 추가해 기존 DB 안에서 벡터 검색을 처리
- **동일 모델 원칙**:
  - 문서 적재와 질문 임베딩에 같은 모델·차원을 사용해야 하며, 변경 시 재임베딩이 필요
