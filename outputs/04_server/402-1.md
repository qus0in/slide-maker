# 모든 요청이 거치는 첫 관문: DispatcherServlet

> **프론트 컨트롤러 패턴 (Front Controller Pattern)**
>
> 모든 요청을 하나의 공통 진입점이 먼저 받아 실제 처리를 위임하는 설계 패턴

- Spring MVC는 URL마다 별도 서블릿을 두지 않고 진입점을 하나로 통일
- `DispatcherServlet`이 그 진입점이며, 실제 처리는 내부 컴포넌트에 위임
- 요청 처리 흐름을 공통 진입점에서 일관되게 조정할 수 있는 구조

# 스프링 부트의 DispatcherServlet 자동 설정

- Spring Boot 4에서는 `spring-boot-starter-webmvc`로 Spring MVC를 구성
- Spring Boot 3 이하 자료에서는 주로 `spring-boot-starter-web`을 사용
- 별도 설정 없이 `/` 경로 전체에 매핑됨
- `web.xml`이나 `WebApplicationInitializer`를 직접 작성할 필요 없음

# 서버 렌더링 요청이 처리되는 대표 흐름

| 단계 | 담당 | 역할 |
| :---: | :--- | :--- |
| 1 | DispatcherServlet | 모든 요청을 최초로 수신 |
| 2 | HandlerMapping | URL에 맞는 컨트롤러(핸들러) 탐색 |
| 3 | HandlerAdapter | 찾은 핸들러를 실제로 실행 |
| 4 | 컨트롤러 | 요청 해석·서비스 호출 후 뷰 이름 반환 |
| 5 | ViewResolver | 논리 뷰 이름을 실제 View로 해석 |
| 6 | View | 데이터를 담아 HTML로 렌더링 |

# 논리 뷰 이름을 실제 경로로 매핑하는 ViewResolver

- 컨트롤러가 반환한 논리 뷰 이름을 실제 템플릿 경로로 변환
- 기본 prefix는 `classpath:/templates/`, 기본 suffix는 `.html`
- 변환 규칙은 `prefix + 논리 이름 + suffix` 형태로 조합됨
- 논리 이름의 슬래시(`/`)는 실제 디렉터리 구조에 그대로 대응

# 화면을 전환하는 두 가지 방법: Forward와 Redirect

- 일반 뷰 이름을 반환하면 View가 곧바로 렌더링됨
- `"forward:/other"`는 서버 내부에서 다른 경로로 흐름만 이관
- `"redirect:/books"`는 302 응답을 보내 브라우저가 새로 요청하도록 유도
- 두 방식 모두 문자열 접두사만으로 동작이 결정됨

# Forward와 Redirect 동작 차이 비교

| 구분 | 요청 횟수 | URL 변화 | 데이터 전달 |
| :--- | :---: | :--- | :--- |
| forward | 1회 | 유지됨 | request 속성 공유 |
| redirect | 2회 | 변경됨 | request 속성 소멸 |

- redirect는 새 요청이므로 이전 request에 담긴 값을 이어받지 못함

# 새로고침으로 발생하는 중복 등록 문제

> **PRG 패턴 (Post-Redirect-Get Pattern)**
>
> POST 처리 후 뷰를 직접 렌더링하지 않고 GET으로 리다이렉트해 재전송을 막는 기법

- POST 처리 후 뷰를 바로 렌더링하면 새로고침 시 같은 POST가 재전송됨
- 재전송된 POST가 등록·수정·삭제를 다시 실행해 중복 처리를 유발
- POST 처리 뒤 GET 요청으로 유도해 이 문제를 차단

# 상황별 응답 분기: 성공(Redirect)과 실패(Render)

- 등록·수정·삭제가 **성공**하면 redirect로 응답해 이후 GET이 화면을 그림
- **검증 실패** 시에는 redirect 없이 폼 뷰를 직접 다시 렌더링
- 실패 케이스에서 redirect를 쓰면 입력값과 오류 메시지가 사라짐

> **입력 정보의 증발 (Data Loss)**
>
> 입력값 검증에 실패했을 때 리다이렉트(Redirect)를 쓰면 브라우저 요청이 완전히 새로 생성되어 사용자가 입력한 값과 오류 정보가 소멸합니다.

# 쿼리 파라미터를 받는 @RequestParam

- 요청 파라미터(쿼리 스트링 또는 폼 데이터)를 핸들러 메서드의 매개변수에 매핑
- 어노테이션에 대상 파라미터 이름을 명시하는 것이 컴파일 최적화 환경에서 가장 안전
- 기본적으로 선언된 파라미터는 필수값(`required = true`)으로 취급됨

# @RequestParam의 세부 속성 활용

- **`value` / `name`**: 바인딩할 요청 파라미터의 이름을 명시
- **`required`**: 필수 여부 설정 (`false` 지정 시 해당 파라미터가 없어도 에러 미발생)
- **`defaultValue`**: 파라미터가 비어있을 때 적용할 기본값을 설정 (설정 시 `required=false` 효과 자동 부여)

> **선택적 파라미터 처리 (Optional)**
>
> `Optional<String>`처럼 선택적 값을 표현하는 컨테이너 타입으로 파라미터 누락을 처리할 수도 있습니다. 이 경우 `required=false`와 같은 의미로 동작합니다.

# 특정 세션 정보만 집중 수신하는 @SessionAttribute

- **세션 정밀 타겟팅**: 세션에서 특정 key에 해당하는 객체만 매개변수로 자동 매핑
- **주요 속성**: `name` (조회할 세션 속성 이름 명시), `required` (해당 속성의 필수 여부 설정)
- **보안 정보 관리**: 직접 서블릿 API(`request.getSession()`)를 조작할 필요가 없어 코드가 간결해짐

# 화면에 일회성 메시지를 뿌리는 Flash Attribute

```java
@PostMapping
String create(@ModelAttribute("bookForm") BookForm form, RedirectAttributes ra) {
    bookService.create(form);
    ra.addFlashAttribute("message", "등록되었습니다.");
    return "redirect:/books";
}
```

> **메시지 미표출 오류 (Muted Message)**
>
> 일반 `Model`은 리다이렉트되는 순간 소멸합니다. 리다이렉트 이후 화면까지 알림 메시지를 운반하려면 `RedirectAttributes`의 `addFlashAttribute`를 써야 합니다.

# 엔티티 보호와 보안을 위한 폼 전용 DTO

> **대량 할당 (Mass Assignment)**
>
> 요청 파라미터가 객체 필드에 그대로 바인딩되어 의도하지 않은 값까지 함께 변경되는 문제

- 요청 파라미터를 영속 엔티티에 직접 바인딩하면 대량 할당 위험이 생김
- 웹 입력 전용 `BookForm` DTO를 쓰고 서비스에서 엔티티로 변환
- 엔티티 구조 변경이 폼 요청 형식에 직접 노출되지 않음

> **대량 할당 보안 취약점 (Mass Assignment)**
>
> 영속성 엔티티에 파라미터를 직접 바인딩하면 악의적인 수정 폼 조작(예: 관리자 필드 임의 주입 등)에 취약해지므로 폼 DTO 분리가 필수입니다.

# 폼 태그에 커맨드 객체를 바인딩하는 th:object

> **선택 변수 표현식 (Selection Variable Expression)**
>
> `th:object`로 지정된 객체를 기준으로 프로퍼티를 참조하는 `*{...}` 표현식

- `th:object`는 폼 전체를 하나의 커맨드 객체에 연결
- 폼 내부에서는 `*{...}`로 그 객체의 프로퍼티에 접근
- `th:field`를 쓰려면 `<form th:object="${...}">` 지정이 먼저 필요

> **폼 객체 누락에 따른 바인딩 오류 (Binding Error)**
>
> Spring 폼에서는 `th:object`와 `th:field="*{...}"`를 함께 사용합니다. 선택 객체나 폼 객체가 없으면 템플릿 처리 중 표현식 평가 또는 바인딩 오류가 발생할 수 있습니다.

# th:action의 경로 계산과 CSRF 토큰 처리

- `th:action="@{...}"`은 애플리케이션의 컨텍스트 경로를 반영해 URL을 생성
- Spring Security가 연동된 POST 폼에는 CSRF 토큰이 hidden input으로 자동 추가
- CSRF 보호가 활성화된 변경 요청은 유효한 토큰이 있어야 처리됨

# 폼의 변경 방식에 따른 DTO 선택

- 요청 한 번으로 완성되는 입력 모델은 불변 `record`가 간결하고 안전함
- 기존 객체를 단계적으로 변경해야 하면 setter를 가진 전용 DTO가 편리할 수 있음
- 동적 행 추가·삭제는 DTO의 불변성보다 폼 필드 구조와 컬렉션 설계가 중요
- 어떤 방식을 쓰더라도 영속 엔티티 대신 입력 전용 DTO로 바인딩 범위를 제한
