# 멀티파트 폼 데이터 개념 정리

- **일반 폼과의 차이**: 텍스트 필드와 파일 파트가 하나의 요청 안에 함께 담겨 전송됨
- **경계 문자열**: 각 파트를 구분하기 위해 요청 헤더에 boundary 값이 포함됨

> **멀티파트 폼 데이터 (multipart/form-data)**
>
> 텍스트와 파일을 여러 파트로 나누어 하나의 HTTP 요청으로 함께 전송하는 인코딩 방식

# 파일은 저장소에, DB에는 이름만

- **이번 차시 저장 위치**: 실습 편의를 위해 `src/main/resources/static/upload`에 직접 저장
- **DB 저장 값**: 원본 파일명과 저장 파일명만 기록하고 파일 본문은 파일 시스템에 저장
- **실서비스 확장**: 운영에서는 애플리케이션 외부 경로나 객체 스토리지를 사용

# 별도 라이브러리가 필요 없는 이유

- **자동 구성**: 웹 스타터가 있으면 멀티파트 처리가 별도 설정 없이 자동 구성됨
- **기본 용량 제한**: 파일 1개 최대 1MB, 요청 전체 최대 10MB
- **다중 파일 주의**: 여러 파일을 한 번에 받으면 요청 전체 크기를 더 크게 잡아야 함

# MultipartFile 주요 메서드

| 메서드 | 의미 |
| :--- | :--- |
| `isEmpty()` | 파일이 첨부되지 않았는지 확인 |
| `getOriginalFilename()` | 클라이언트가 보낸 원본 파일명 조회 |
| `getContentType()` | 클라이언트가 보낸 MIME 타입 조회 |
| `getSize()` | 파일의 바이트 크기 조회 |
| `transferTo(Path)` | 지정 경로로 파일 내용을 저장 |

# 클라이언트가 보낸 값은 믿지 않는다

- **신뢰 불가 값**: `getOriginalFilename()`, `getContentType()`은 모두 클라이언트가 보낸 값
- **원본 이름 그대로 저장 시 위험**: 이름 충돌과 경로 조작(path traversal) 문제 발생 가능
- **서버 측 대응**: 서버가 UUID로 새 파일명을 생성해 저장

# 컨트롤러가 파일 저장을 직접 하지 않는 이유

- **중복 발생**: 파일명 생성, 저장 경로 계산, 확장자 검증이 컨트롤러마다 반복됨
- **변경에 취약**: 저장 방식(로컬 → 클라우드 등)이 바뀌면 관련된 모든 컨트롤러를 수정해야 함
- **책임 분리**: 파일 저장은 `FileStore` 한 곳에서만 담당하고, 컨트롤러는 요청 처리에 집중

# 원본 이름과 저장 이름을 함께 다루는 이유

- **사용자용 이름**: 화면에 보여주거나 다운로드할 때는 원본 파일명이 필요함
- **서버용 이름**: 실제 파일에 접근할 때는 충돌 없는 저장용 이름이 필요함
- **작은 객체로 묶기**: 두 이름을 함께 반환할 작은 객체가 있으면 이후 처리가 단순해짐

# FileStore가 파일을 저장하는 4단계

| 단계 | 목적 |
| :--- | :--- |
| **형식 검증** | 확장자·크기·파일 시그니처를 함께 확인함 |
| **디렉터리 준비** | 저장 폴더가 없으면 새로 생성함 |
| **UUID 이름 생성** | 파일명 충돌과 경로 추측을 방지함 |
| **실제 파일 저장** | 검증을 통과한 파일만 지정 경로에 씀 |

# FileStore 컴포넌트의 기본 골격

```java
@Component
public class FileStore {

    private static final Set<String> ALLOWED_EXTENSIONS =
            Set.of("jpg", "jpeg", "png", "gif", "webp");

    private final Path uploadPath =
            Path.of("src/main/resources/static/upload")
                    .toAbsolutePath().normalize();
}
```

# 허용 확장자 목록으로 1차 검증

```java
if (file == null || file.isEmpty()) return null;
String originalName = Objects.requireNonNull(file.getOriginalFilename());
String safeName = StringUtils.getFilename(
        StringUtils.cleanPath(originalName));
String extension = StringUtils.getFilenameExtension(safeName);
if (extension == null) throw new IllegalArgumentException("확장자 없음");
extension = extension.toLowerCase(Locale.ROOT);
if (!ALLOWED_EXTENSIONS.contains(extension))
    throw new IllegalArgumentException("지원하지 않는 형식입니다.");
```

# UUID 이름 생성과 경로 이탈 검사 후 저장

```java
Files.createDirectories(uploadPath);
String storedName = UUID.randomUUID() + "." + extension;
Path target = uploadPath.resolve(storedName).normalize();

if (!target.startsWith(uploadPath)) {
    throw new IllegalArgumentException("잘못된 저장 경로입니다.");
}

file.transferTo(target);
return new UploadFile(safeName, storedName);
```

# 저장 과정에 필요한 방어 계층

- **`createDirectories`**: 폴더가 없으면 만들고, 이미 있으면 그대로 통과함
- **UUID 이름**: 사용자 입력을 저장 경로에 쓰지 않고 이름 충돌도 방지함
- **경로 검사**: 정규화한 대상이 `static/upload` 폴더 안에 있는지 확인함
- **콘텐츠 검증**: 확장자·크기와 함께 파일 시그니처를 검사하고 필요하면 재인코딩함

# 파일 업로드 폼이 지켜야 할 조건

- **필수 속성**: `<form>`에 `method="post"`와 `enctype="multipart/form-data"` 반드시 지정
- **이름 일치**: `input`의 `name`이 컨트롤러 파라미터 이름과 정확히 일치해야 함
- **`accept` 속성의 한계**: `accept="image/*"`는 선택 편의 기능일 뿐, 서버 측 검증을 대신하지 않음

# 1:1 관계 — 사용자와 프로필 이미지

- **부분 갱신**: 새 파일을 선택하지 않으면 기존 값 유지

# cascade와 orphanRemoval이 하는 일

- **cascade**: Book을 저장하면 컬렉션에 담긴 BookImage도 함께 저장
- **orphanRemoval**: 관리 중인 컬렉션에서 빠진 BookImage는 플러시 때 DB에서 삭제됨
- **한계**: `static/upload`의 실제 파일은 지워지지 않아 파일 삭제 코드를 별도로 호출해야 함

# 실습 방식과 실제 서비스의 차이
