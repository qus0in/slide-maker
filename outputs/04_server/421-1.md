# SSR에서 REST로: 서버 책임의 이동

- **기존 SSR**: 컨트롤러가 `Model`을 채우고 Thymeleaf가 완성된 HTML을 렌더링
- **이번 차시부터**: 컨트롤러는 뷰 이름 대신 데이터(JSON)만 반환
- **화면 책임 이동**: 화면을 그리는 일은 클라이언트(웹, 모바일, 다른 서버)의 몫
- **본질**: 반환 타입 변경이 아니라 서버·클라이언트 책임 재분배 설계 문제
- **환경**: Spring Boot 4.1(Spring Framework 7) 기준, `spring-boot-starter-webmvc` 사용

# SSR과 REST API 비교

| 구분 | SSR (Thymeleaf) | REST API |
| :--- | :--- | :--- |
| 응답 본문 | 완성된 HTML | JSON 데이터 |
| 요청 간 상태 | 세션 활용이 흔함 | 각 요청이 문맥 포함(무상태) |
| 화면 책임 | 서버가 화면을 완성 | 클라이언트가 화면을 구성 |
| 재사용성 | 이 화면 전용 | 웹·모바일·서버가 함께 사용 |

- 같은 `GET /boards`도 SSR은 HTML 문서를, REST는 목록 JSON을 반환

# REST란 무엇인가

> **REST (Representational State Transfer)**
>
> 로이 필딩의 박사 논문에서 제시된, 자원을 표현(representation) 형태로 주고받는 분산 시스템 설계 스타일

- 제약을 모두 만족하면 RESTful하다고 부름
- REST는 프로토콜이 아니라 아키텍처 스타일

---
layout: default
---

# REST의 제약 조건

| 제약 조건 | 의미 |
| :--- | :--- |
| 클라이언트-서버 | 화면과 데이터 저장을 분리해 독립적으로 발전 |
| 무상태(Stateless) | 요청 간 클라이언트 상태를 보관하지 않음 |
| 캐시 가능 | 응답의 캐시 가능 여부를 명시 |
| 계층화 | 프록시·게이트웨이 존재를 클라이언트가 몰라도 됨 |
| 균일한 인터페이스 | 리소스 식별, 표현 조작, 자기 서술적 메시지, HATEOAS |
| (선택) Code-on-Demand | 서버가 실행 코드를 내려 클라이언트 기능 확장 |

---
layout: default
---

# 무상태(Stateless)가 뜻하는 것

- **의미**: 이전 요청의 대화 문맥에 의존하지 않고 각 요청만으로 처리 가능해야 함
- **오해 정정**: 서버가 DB·캐시·세션을 안 쓴다는 뜻이 아님
- **인증 반영**: 매 요청에 쿠키나 `Authorization` 헤더가 함께 전달돼야 함
- **JWT는 선택지**: REST의 필수 조건이 아니며, `HttpOnly` 세션 쿠키 방식도 널리 쓰임

# JSON이 사실상 표준이 된 이유

- **JS 생태계 결합**: `JSON.parse()`, `JSON.stringify()` 내장
- **간결한 텍스트 표현**: XML 대비 태그·엔벨롭 오버헤드가 적음
- **가독성**: Key:Value, 배열, 숫자, 문자열, 불리언, null만으로 구성
- **언어 독립 표준(RFC 8259)**: 거의 모든 언어가 파서를 기본 탑재

# 흔한 URI 설계 실수

| 나쁜 예 | 좋은 예 | 이유 |
| :--- | :--- | :--- |
| `GET /getBoards` | `GET /boards` | 동사 대신 메서드로 표현 |
| `POST /boards/create` | `POST /boards` | 컬렉션에 POST면 충분 |
| `GET /boards/1/delete` | `DELETE /boards/1` | 삭제는 DELETE 메서드로 |
| `POST /updateBoard?id=1` | `PUT /boards/1` | 리소스는 경로, 동작은 메서드 |
| `GET /Boards/1` | `GET /boards/1` | 소문자 규칙 준수 |

- **표기 규칙**: 복수 명사·소문자·하이픈을 쓰고 확장자와 끝 slash는 붙이지 않음
- **계층 표현**: 하위 리소스는 `/boards/{id}/comments`처럼 경로로 표현

# HTTP 메서드의 안전성과 멱등성

| 메서드 | 안전 | 멱등 | 본문 | 게시판 예시 |
| :--- | :--- | :--- | :--- | :--- |
| GET | O | O | 없음 | `GET /boards/1` |
| POST | X | X | 있음 | `POST /boards` 생성 |
| PUT | X | O | 있음 | `PUT /boards/1` 전체 교체 |
| PATCH | X | 보장 안 됨 | 있음 | `PATCH /boards/1` 부분 수정 |
| DELETE | X | O | 보통 없음 | `DELETE /boards/1` |

- PUT은 리소스 전체를 교체하고, PATCH는 지정한 필드만 수정

# 실패를 알리는 상태 코드

| 코드 | 이름 | 언제 |
| :--- | :--- | :--- |
| 400 Bad Request | 잘못된 요청 | 형식 오류, 검증 실패 |
| 401 Unauthorized | 인증 안 됨 | 인증 정보 없음/무효 |
| 403 Forbidden | 권한 없음 | 인증됐으나 접근 권한 없음 |
| 404 Not Found | 리소스 없음 | 해당 id 리소스 부재 |

| 500 Internal Server Error | 서버 오류 | 예상치 못한 내부 오류 |

- 401은 "누구인지 확인 안 됨", 403은 "확인됐지만 권한 없음"

# OpenAPI 명세와 Swagger UI의 역할

> **OpenAPI 명세 (OpenAPI Specification)**
>
> API의 경로·요청·응답 구조를 정의하는 JSON/YAML 규격

- **명세는 규격**: API 계약을 기계가 읽을 수 있는 형태로 표현
- **Swagger UI는 뷰어이자 테스트 도구**: 명세를 화면에 렌더링하고 요청까지 보낼 수 있게 함
- **자동 생성**: springdoc이 컨트롤러·DTO를 분석해 기본 명세를 만들어 줌

# @RestController가 대신 해주는 일

- **합성 애너테이션**: `@Controller` + `@ResponseBody`를 합쳐 놓은 것
- **반환값이 곧 본문**: 메서드 반환값 자체가 응답 본문이 됨
- **뷰 리졸버 생략**: 반환값이 뷰 리졸버를 거치지 않고 바로 변환됨
- **Boot 4 기본 컨버터**: Jackson 3 기반 `JacksonJsonHttpMessageConverter` 사용
- **문자열 반환 주의**: 뷰 이름이 아니라 순수 텍스트 본문 그대로 나감

# 요청 매핑 어노테이션

| 어노테이션 | HTTP 메서드 | 용도 |
| :--- | :--- | :--- |
| `@RequestMapping` | 전체 또는 `method` 지정 | 클래스 공통 경로 |
| `@GetMapping` | GET | 조회 |
| `@PostMapping` | POST | 생성 |
| `@PutMapping` | PUT | 전체 수정 |
| `@PatchMapping` | PATCH | 부분 수정 |
| `@DeleteMapping` | DELETE | 삭제 |

- **불일치 시 오류**: `produces` 불일치는 406, `consumes` 불일치는 415

# 핸들러 파라미터가 값을 꺼내는 위치

| 어노테이션/타입 | 값 위치 | 언제 |
| :--- | :--- | :--- |
| `@PathVariable` | 경로 템플릿 변수 | 리소스 식별 |
| `@RequestParam` | 쿼리 스트링, 폼 | 검색어·페이지 번호 |
| `@RequestBody` | 요청 본문 전체 | JSON을 DTO로 역직렬화 |
| `@ModelAttribute` | 여러 요청 파라미터 | 파라미터를 필드에 바인딩 |
| `@RequestHeader` | 요청 헤더 | 인증 토큰 등 |
| `@CookieValue` | 쿠키 | 세션 식별자 등 |
| `@RequestPart` | 멀티파트 파트 | 파일 업로드 |
| `Pageable` | `page`,`size`,`sort` | 페이징·정렬 조건 |

# @RequestBody와 @ModelAttribute의 차이

- **@RequestBody**: 본문 하나를 Jackson이 통째로 역직렬화
- **@ModelAttribute**: 쿼리·폼의 개별 파라미터를 필드에 하나씩 바인딩
- **혼용 불가**: JSON 본문에 `@ModelAttribute`를 쓰면 바인딩되지 않음

# REST에서 BindingResult를 두지 않는 이유

- **SSR의 관례**: `BindingResult`로 검증 실패를 잡아 같은 폼 뷰로 되돌아감

- **일관 변환은 Advice에서**: `@RestControllerAdvice`가 오류 응답으로 변환(형식 변환은 다음 차시)

# ResponseEntity 팩터리 메서드 (1/2)

| 시작 메서드 | 상태 | 반환 빌더 | 주요 용도 |
| :--- | :--- | :--- | :--- |
| `ok()` | 200 OK | `BodyBuilder` | 조회 및 수정 성공 시 데이터와 함께 반환 |
| `created(uri)` | 201 Created | `BodyBuilder` | 리소스 생성 성공 및 `Location` 헤더 전달 |
| `accepted()` | 202 Accepted | `BodyBuilder` | 비동기 작업 요청 접수 완료 |
| `noContent()` | 204 No Content | `HeadersBuilder` | 본문 없이 성공 상태만 전달 |

- **`HeadersBuilder` 특징**: `body()` 메서드가 생략되어 204 응답에 실수로 본문을 포함하는 오류를 차단함

# ResponseEntity 팩터리 메서드 (2/2)

| 시작 메서드 | 상태 | 반환 빌더 | 주요 용도 |
| :--- | :--- | :--- | :--- |
| `badRequest()` | 400 Bad Request | `BodyBuilder` | 요청 파라미터 또는 본문 검증 실패 처리 |
| `notFound()` | 404 Not Found | `HeadersBuilder` | 요청한 리소스가 존재하지 않음을 반환 |
| `status(status)` | 동적 지정 | `BodyBuilder` | 표준 메서드가 없는 상태 코드(예: 409, 422) 지정 |

- **`HeadersBuilder` 특징**: `notFound()` 또한 본문 없이 404 헤더 응답을 명확히 조립함
- **`status(...)` 활용**: `HttpStatus` Enum 또는 숫자 코드를 전달하여 상황별 응답을 자유롭게 구사함

# 본문 없는 응답을 표현하는 `Void`

- **void 키워드**: 자바 키워드라 제네릭 타입 인자로 쓸 수 없음
- **Void 참조 타입**: 값이 없음을 제네릭에서 표현하며 인스턴스를 만들 수 없음
- **계약 표현**: `ResponseEntity<Void>`는 상태·헤더만 반환하고 본문은 없다는 뜻
- **자동 204 아님**: 반환 타입이 `void`라도 상태 코드가 자동으로 204가 되지는 않음
- **삭제 응답**: `ResponseEntity.noContent().build()`로 본문 없이 204를 명시

# ResponseEntity와 DTO 직접 반환의 선택 기준

| 상황 | 선택 | 이유 |
| :--- | :--- | :--- |
| 상태 고정, 헤더 불필요 | DTO 직접 반환 + `@ResponseStatus` | 시그니처가 간결 |
| 상태가 조건에 따라 달라짐 | `ResponseEntity` | 분기하며 동적 결정 |
| `Location` 등 헤더 필요 | `ResponseEntity` | 본문과 헤더를 함께 구성 |
| 본문 없는 성공(204) | `noContent().build()` | 본문 타입 강제 없음 |

# 수정·삭제 응답을 정하는 기준

- **수정 응답 선택**: 변경된 리소스 본문과 함께 `200 OK`를 반환하거나, 본문 없이 `204 No Content` 반환 중 팀 컨벤션으로 통일
- **삭제 응답 관례**: 삭제 성공 시 본문 없이 `204 No Content` 반환이 표준 관례
- **시간 표현 규격**: 생성·수정 시각은 `Instant` 타입으로 통일하고 UTC ISO 8601 형식(`2026-08-12T14:30:00Z`)으로 반환
- **동시성 보호 필요성**: 여러 사용자가 동시에 동등한 대상을 수정할 때 덮어쓰기(Lost Update)를 방지하는 검증 계약 필요

# 동시 수정 제어: ETag와 If-Match

> **ETag (Entity Tag)**
>
> 리소스의 특정 상태나 버전을 식별하기 위해 서버가 응답 헤더로 전달하는 고유 해시/버전 값

- **`ETag` (응답 헤더)**: `GET` 조회 시 서버가 해당 리소스의 현재 버전 식별자를 전달 (`ETag: "v1.0.2"`)
- **`If-Match` (요청 헤더)**: `PUT`/`PATCH` 수정 요청 시 클라이언트가 조회했던 기존 버전 식별자를 첨부
- **충돌 검증 흐름**:
  - **버전 일치**: 수정 승인 후 `200 OK` (새 `ETag` 발행)
  - **버전 불일치**: 다른 사용자가 먼저 수정했으므로 `412 Precondition Failed`로 덮어쓰기 차단

# Page를 그대로 반환하지 않는 이유

- **내부 구현 종속**: `Page<T>`를 그대로 반환하면 JSON 구조가 `PageImpl` 내부 구현에 묶임
- **공식 경고**: Spring Data도 `Page` 직접 노출을 권장하지 않는다고 명시
- **계약 고정**: 클라이언트가 실제로 쓰는 필드만 골라 응답 계약으로 못 박음

- **과잉 주석 경계**: 기계적으로 모든 필드를 반복 표기하면 구현과 문서가 함께 복잡해짐
